# Tennis Checkの練習編集

このskillはリポジトリルートの`.agents/skills/tennis-drill-authoring/`に置く。以下のコードパスとコマンドはリポジトリルート基準。

動画調査やskillの検証だけを依頼された場合は、確認した内容・既存項目との関係・手順の改善を報告する。カタログへの追加・更新まで依頼されている場合にデータへ反映する。

## 調査と編集

1. [データ規則](../../../data/README.md)と`src/types/catalog.ts`を読み、該当カテゴリの既存項目を確認する。コート図を扱う場合は[設計書](../../../docs/DESIGN.md)も読む。
2. `data/drills/`と`data/sources.json`でID、名称、別名、タグ、URLを検索する。同じ動作でも目的・制約・チェックポイントが異なる場合は別項目にできる。既存の資料IDとタグを優先して再利用する。
3. 参考資料の該当箇所を実際に確認する。YouTubeは[動画確認手順](references/youtube.md)に従い、yt-dlpで動画をダウンロードして映像を解析する。タイトル・説明文・字幕だけから動作を推測しない。
4. 通常は`pnpm dev`の`#/editor`で対象カテゴリへ保存する。まとまった変更やUIを操作できない環境ではJSONの直接編集も可能。対象範囲だけを2スペースインデントで編集し、同じ検証を通す。エディタを開いている場合は外部変更後に再読み込みする。
5. 概要、セットアップ、手順、チェックポイント、成功条件、失敗例、安全上の注意を整合させる。資料にない回数や配置を追加した場合は、資料の事実とカタログでの応用を区別する。医療・リハビリの処方を断定せず、痛みが関係する項目には安全上の注意を入れる。

## データの整合

- 公開済みの練習IDは変更しない。保存済みの参考資料IDと練習の大分類も維持する。
- 人数、環境、用具、強度、時間は自由タグではなく対応する構造化フィールドへ入れる。
- `sources`は内容の根拠、`media`は詳細画面に表示する資料。どちらも資料IDの文字列配列で、オブジェクトや`timestamp`フィールドを追加しない。
- 新しい資料は`data/sources.json`へ`id`、`title`、`organization`、`kind`、`url`、`note`を登録する。確認した時間帯・動作・判断基準は`note`へ書く。
- `researched`は資料に直接対応する内容、`derived`は資料の原則から構成した応用、`draft`は根拠や内容が未確認。映像を確認できなかった項目を確認済みと扱わない。
- 参考画像は`public/images/drills/`へ保存し、`image.alt`と`image.credit`を設定する。`image.src`と表示側の`import.meta.env.BASE_URL`の組み合わせを確認する。
- コート座標は左上`(0, 0)`、右下`(100, 100)`。`diagram.phases`の順序と、人物、球出し、用具、球道、移動、狙いを文章に合わせる。
- 項目の追加・削除後は`data/catalog.json`のカテゴリ件数と合計件数を合わせる。カタログ更新時は`updatedAt`も確認する。READMEへ件数を複製しない。

## 完了確認

- `pnpm check`でlint、実データ検証を含むテスト、型チェック、ビルドを通す。新しいデータ制約や表示動作を導入した場合は対応するテストを追加・更新する。
- 一覧から名称またはタグで検索し、変更した項目の詳細を開く。デスクトップ幅とモバイル幅で横はみ出し、文字の重なり、画像の欠落を確認する。
- コート図があれば配置・軌道・狙い・フェーズ切替を確認する。参考画像やリンクはGitHub Pagesのベースパス付きURLも確認する。
- `git diff`と`git status`で対象外の変更や調査用動画が含まれていないことを確認する。完了報告には変更項目、確認した出典・時間帯、検証結果、未確認事項を簡潔に記載する。
